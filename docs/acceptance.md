# 验收标准与技术验证清单

> 文档版本：v0.1（规划稿）
> 原则：**每项技术栈都要有"可截图、可复现、可解释"的证据**，不接受"已加依赖"作为验证结果。

---

## 1. 验收总则

| 编号 | 原则 |
| --- | --- |
| P1 | 技术栈验证必须有操作步骤 + 预期输出 + 证据（截图/日志/接口响应） |
| P2 | 功能验收以三种角色的真实操作为准，不以接口单测替代端到端 |
| P3 | 分布式事务以**故障注入后的数据状态**为准，不以"没报错"为准 |
| P4 | 部署验收在目标 Linux 服务器从零执行，不在开发机"模拟" |
| P5 | 演示脚本可重复执行，重复执行不产生脏数据（或提供重置脚本） |

## 7. 答辩问答准备（预判）

| 问题 | 应答要点 |
| --- | --- |
| 为什么 AI 结果不能直接决定审核？ | 模型输出不确定、可能幻觉；业务责任在人；后端做 7 项校验并只作建议；最终值由管理员确认 |
| Seata 为什么只覆盖审核派单？ | 只有这里需要跨两库原子写；AI/地图是外部不可回滚资源，MQ 是异步最终一致，纳入全局事务会导致长事务与悬挂 |
| 为什么不用 Spring Security？ | 团队选型统一，Sa-Token 更轻量，网关与微服务共用 Redis 会话，避免双认证体系 |
| 为什么拆 AI/地图服务而不拆通知服务？ | AI/地图有独立外部依赖、独立限流熔断与日志，复用方多；通知量小且无独立数据，拆分无收益 |
| 消息重复消费怎么办？ | `messageId` + Redis `SETNX` 幂等键 + 业务唯一键（`uk_wo_event_id`）+ 状态条件更新 |
| 工单并发接单如何保证？ | `UPDATE ... WHERE id=? AND status='PENDING_ACCEPT'`，受影响行数为 0 即冲突，配合 `version` 乐观锁 |
| 事件与工单状态不一致怎么办？ | MQ 最终一致 + 消费幂等 + 每日对账任务告警（可选增强） |
| 为什么不用分库分表？ | 数据量小，拆分带来部署与排错成本；按服务垂直分库已满足数据归属要求 |
| Docker 部署遇到什么坑？ | 记录实际踩坑（如 Nacos gRPC 端口、Seata 配置中心、时区），写入 `docs/` 踩坑记录 |
